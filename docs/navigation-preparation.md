# Offline navigation and graph approval

The Map screen now provides walking-route planning controls, independent endpoints, optional foreground GPS, provisional map pins, place Directions and route display. Actual guidance remains unavailable until a separately reviewed core graph is installed. The visual coverage buffer is not a walking service region. Display-only context features explicitly carry `navigation_eligible: false`; geometry remains in longitude/latitude in both map modes. An OSM footway or entrance observation alone is insufficient access or connectivity evidence.

Reuse `src/routing/engine.ts` contracts rather than create another graph: `Node` carries coordinate, grade, barrier and review; `Edge` carries exact geometry, direction, foot/access state and grade transition; `Connector` connects an explicit endpoint to an edge, optionally through `entranceId`. Existing directory `Entrance` carries its coordinate, floor and eligibility. Their evidence IDs must refer to source-backed reviewed observations. Retain original coordinates and source lineage; never derive route vertices from decorative trees, rendered roofs or screenshot pixels.

The next ingestion milestone must bind each place entrance to the existing place identity, source snapshot and source evidence, establish pedestrian access, and distinguish public crossings from grade-separated intersections. Equal screen positions do not establish graph connectivity. Node/edge connectivity, endpoint consistency, barrier status, permitted direction, grade transitions and fresh review are validated by the existing engine. Route snapping must use eligible reviewed edges and verified entrance connectors; it must not silently cross a road or attach to the nearest building centroid. Preserve the engine's bounded snap distance and reject an uncertain connector instead of inventing an access path. A boundary expansion needs a new reviewed graph loader; the current loader deliberately accepts only the original pilot boundary.

`src/routing/installed.ts` independently verifies active-pack hashes, scope, version, snapshot, bytes and rights expiry before graph installation. `src/updates/` already provides content-addressed installation, resumable downloads, verification and rollback. Its locally reviewed catalog and manifest digest registry remain empty because no new distributable content pack or pedestrian graph has been approved. Do not populate either from download metadata or the display-context receipt. Preserve existing conversations, directory persistence, model files and optional foreground location when future packs are introduced.

`calculateWalkingRoute` accepts symmetric manual/GPS/place endpoints. Place endpoints require approved entrance connectors; map pins retain their raw position and require defensible network attachments within the existing 15 m bound. Directed virtual edge splits let all eligible attachment/entrance alternatives compete by total nonnegative distance-equivalent cost. GPS freshness/uncertainty, source refresh, foreground, graph review expiry and asynchronous request generations can invalidate displayed guidance. Clear removes endpoints; Exit keeps the shared session origin. Back cancels a draft, then collapses instructions, then exits.

The retained-input builder and its optional horizontal/vertical corner assumption produce **candidate-only** graphs; [walking-graph.md](walking-graph.md) records exact source hashes, topology diagnostics and evidence still blocking approval. The fallback uses compatible shared source junctions and preserves restrictions and grade separation. It does not establish measured sidewalks or verified crossings. No candidate is installed by the app. No ETA, automatic rerouting or continuous/background GPS tracking is added. Host geometry checks do not establish real-world walkability or physical-device acceptance.
